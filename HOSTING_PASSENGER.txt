Passenger production checklist (Valitsa Travel)
==============================================

1) Hosting panel (required if ERR_REQUIRE_ESM or generic Passenger error)
   - Application root: the directory that contains THIS repo's package.json and passenger_entry.cjs (not server/ alone).
   - Startup file: passenger_entry.cjs
   - Save, then restart the Node/Passenger app (or touch tmp/restart.txt if your host documents that).

2) After restart — get the real error
   - Open the site error page and click "Technical details for the administrator of this website."
   - Also read application stdout/stderr in the hosting panel.
   - If logs still show require() of server/index.js, the startup file in the panel is still wrong.

3) On the server (SSH or file manager)
   - Confirm passenger_entry.cjs exists next to package.json in the deployed path.
   - Confirm git revision matches what you expect: git rev-parse --short HEAD

4) Local verification before deploy
   - npm run verify:deploy

5) Client routes (/trips, /admin/login, …)
   - Run `npm run build` on the server or in CI so `dist/index.html` exists next to `package.json`.
   - Without `dist/`, Express cannot serve the SPA; deep links will 404.

6) Nginx in front: .htaccess does not apply. If GET https://your-domain/api/health returns HTML or 404 (not JSON), /api is not reaching Express on that hostname.

   Path A — single origin (no extra frontend env):
   - Passenger application root must be the same tree as the live site (package.json + passenger_entry.cjs + dist/), OR nginx must proxy location /api/ to Node. Paste block from deploy/nginx-api-location.include.conf above static try_files (also see deploy/nginx-spa-snippet.conf Option B).

   Path B — main site static, API on another host (subdomain or internal URL):
   - Find a base URL where GET /api/health returns {"ok":true,...} (e.g. https://api.yourdomain.gr).
   - In root .env before npm run build: VITE_API_BASE_URL=https://api.yourdomain.gr (no trailing slash). Rebuild and deploy dist to the main site.
   - On the API server, server/.env CORS_ORIGIN must include https://yourdomain.gr

7) After every deploy (recurring check):
   - Restart Passenger (e.g. touch tmp/restart.txt — see .cpanel.yml) or use the panel restart.
   - From your machine: npm run verify:api-health
     (or: API_HEALTH_URL=https://yourdomain.gr npm run verify:api-health)
   - Pass = GET /api/health returns JSON with "ok": true. Fail = HTML or 404 → Path A or B above is still required.

8) Optional strict build (Path B only): CHECK_PRODUCTION_API=1 npm run build
   - Fails the build if VITE_API_BASE_URL is unset — use in CI when you always deploy with a separate API origin.

9) cPanel — create an API subdomain (Path B when the main domain never serves JSON on /api)
   - Subdomains → add e.g. api → document root MUST be the same folder as your Node app (where package.json and passenger_entry.cjs live), e.g. ~/valitsa_app — not a copy of dist/ only.
   - Enable SSL (AutoSSL) for api.yourdomain.gr, wait for DNS if needed.
   - Test: curl -s https://api.yourdomain.gr/api/health  → must print JSON with "ok":true.
   - In project root .env: VITE_API_BASE_URL=https://api.yourdomain.gr (no trailing slash). npm run build. Upload the new dist/ to the main domain (valitsatravel.gr can stay on static nginx).
   - server/.env on the API machine: CORS_ORIGIN must include https://valitsatravel.gr (and https://www.… if you use it). Restart Node after editing.

10) "Last time I only uploaded dist and it worked" — what that can (and cannot) fix
   - CAN: A fresh dist/ brings an updated dist/.htaccess (no /index.html → / 301, SPA rewrites). That fixes redirect loops and routing issues on Apache or when Apache still sees .htaccess behind nginx.
   - CAN: Git deploy (.cpanel.yml + rsync) + tmp/restart.txt restarts Passenger. If Node had crashed or was stale, /api can work again on the same hostname without a new subdomain.
   - CANNOT: If the edge server (nginx) serves static files only for the main domain and never forwards /api to Node, another dist upload alone will not make /api/health return JSON — use section 6 Path A or B.
   - If you are unsure: curl -s https://your-domain/api/health — JSON means Path A is OK; HTML means you still need 6 or 9.
